## Orden operativo exacto

El recorrido de producto será acceso → anamnesis → mesociclo → historial → semana/check-in → análisis → chat → propuesta → reviewer → aceptación → revisión siguiente. Hay una dependencia técnica: **provision crea primero el mesociclo en draft**, porque guardar anamnesis requiere su UUID; enviarla después lo activa. No crear un mesociclo ficticio desde el browser.

Notación: `U` es el UUID confirmado de Patata; `R` la rutina expresamente aprobada para Premium; `M` el UUID devuelto por provision; `N` la revisión actual leída del servidor; `W` la `tracking_week` actual; `K` una clave nueva para una acción explícita. No reutilizar IDs de fixtures.

## Adapter productivo necesario

`PremiumChat.mount(container, adapter, options)` es el componente preparado. El host deberá implementar sus actions con la **sesión del usuario actual**, no con las credenciales del harness:

- `state` → `premium_chat_load(M)` y `PremiumChat.fromBackend(...)`. Solo proyección segura; nada de context_bundle, receipt o secrets.
- `permission` → `premium_chat_permission(M, allow)` y relectura de estado. La casilla no concede acceso antes de confirmarlo el servidor.
- `send` / `retry` → Edge `simple-coach-chat` con el body cerrado de cuatro campos. Conservar la clave/ID pendiente para reconciliar mediante lectura; no reenviar automáticamente al recargar.
- `proposal` → lectura RLS de la recomendación autorizada o navegación al flujo Premium existente de propuesta/reviewer/aceptación. No reconstruir patches desde el texto del mensaje ni añadir Aplicar dentro del chat.
- `navigate` → volver al espacio SIMPLE Coach existente, sin destinos de preview o cambios de autenticación.

Anamnesis, calendario, check-in y reviewer también requieren adapters reales. El envío semanal usa el Edge ya citado; consultar `premium_weekly_provider_context(p_mesocycle uuid)` es una lectura de contexto, no una llamada al modelo. La cola Premium se consulta mediante las tablas/RLS y asignación explícita existentes: no se inventa una RPC nueva ni se amplían los permisos de la cola Basic.

## Comprobaciones y puntos de parada del piloto

Antes de admitir, guardar un baseline de solo lectura de identidad/cantidad/campos estables de Auth, perfil, rutinas, días/ejercicios, workouts, asignaciones/notas, gestión/revisiones y operaciones Basic. No usar updated_at/last_sign_in_at como prueba única de identidad ni modificar Auth para ajustar hashes.

Durante el recorrido, el titular podrá primero preguntar por un ejercicio de su rutina, progreso registrado o RIR/descanso. Una petición concreta de ajuste se hará solo si la desea. Se registran metadatos sanitizados de cada dispatch, coste/reserva, estado persistido y warnings. No se obliga a gastar hasta obtener MODIFY ni se añaden datos sintéticos para provocar adaptación.

Detenerse ante UUID/rol inesperado, cuenta/rutina ajena, mapping ambiguo, prescripción irresoluble, ausencia de autorización/periodo/budget, stale/revocation, error de proveedor, output inválido o diferencia de datos fuera del patch autorizado. No reintentar, fusionar cuentas, corregir datos o aprobar automáticamente.

El cierre debe confirmar usuario/rol originales; Core/Basic intactos; grants explícitos; mensajes y propuestas únicos; reviewer restringido; aceptación propia; inmutabilidad de `N`; y datos vivos iguales a la revisión aceptada. Si no aparece una propuesta justificable, registrar ese resultado y dejar N+1 pendiente en vez de simular que se probó.
