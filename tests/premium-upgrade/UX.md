# Premium Phase 5 — revisión del host unido

`frontend-design` mantiene la dirección aprobada: tokens existentes `theme.css`, Arial, crema/piedra/antracita, bordes finos y sin Atlas, slogans, imágenes anatómicas ni un rediseño de Basic. El home usa jerarquía de texto y una acción de check-in; el menú común ofrece Hoy / Semana, Mi programación, Check-in, Análisis y Chat.

## Correcciones concretas

| Problema | Cambio | Beneficio | Comprobación |
|---|---|---|---|
| Las antiguas previews separaban anamnesis, seguimiento, análisis y chat | Un solo host y navegación, con estados aislados por pantalla | La cuenta sigue la misma rutina/revisión sin saltar entre demos | Navegación común, ambos recorridos de adopción, chat después de aceptar N+1 |
| Un rol client no acredita Premium | Gate del servidor antes del montaje real; capabilities/grants independientes | Solo usuarios autorizados acceden al piloto | SDK sin sesión / gate disabled; mocks denied/expired y pruebas JWT del root separadas |
| Una comparación JSON.stringify puede fallar por orden de claves JSONB | Comparación canónica de objetos después de releer | Se confirma el dato guardado sin declarar error por serialización | Objetos con claves reordenadas; arrays con orden distinto siguen siendo diferentes |
| Snapshots antiguos no siempre tienen target/reps | Lectura explícita de reps_min/reps_max y campos legacy, sin reconstruir | Prescripción antigua legible y UUID intactos | Caso legacy y prescripción por serie heterogénea |
| Un select podía incluir sus opciones en el nombre accesible | aria-labelledby al texto concreto | Lectores de pantalla/teclado identifican cada día claramente | Anamnesis completa real de la UI, seleccionando minutos por label exacto |
| Dos pestañas pueden guardar sobre un borrador/version anterior | Separación por UUID/revisión/row_version y conflicto visible | Se evita sobrescritura stale y se conservan respuestas | Conflicto de servidor y evento storage entre dos pestañas |
| La petición tardía podía cambiar una pantalla abandonada | Epoch por navegación; relectura con ticket | El usuario permanece en su destino actual | Estado tardío después de pasar a Mi programación |
| Una propuesta aplicable necesita contexto y warnings | Antes/después legible y warnings antes de la confirmación | El atleta y reviewer pueden valorar el cambio antes de aceptar/aprobar | Propuesta estructurada, permiso revocado y aceptación confirmada seguida de nueva revisión |
| Formularios/chat requieren poco ancho y teclado | Un scroll principal; chat mantiene su propio scroll de mensajes dentro del host sin otro scroll exterior | Se puede completar sin deslizamiento horizontal ni pie escondido | 320/360/390/430/1280, ambos motores y temas; altura de teclado simulada |
| El candidato necesitaba una entrada desde la aplicación real | Botón secundario independiente de Basic, condicionado al gate del servidor, y diálogo con el SDK actual | El recorrido está disponible para el piloto autorizado sin concederse Premium localmente | `host.cjs`: gate OFF/ON, RPC ausente, error, localStorage irrelevante, carga, navegación y cambio de sesión |
| Una anamnesis parcial podía lanzar una excepción al normalizar | Validación de forma previa y aviso si un intake enviado no puede confirmarse; catch reconstruye el aviso como texto | No se inventan respuestas ni aparece un montaje incompleto como éxito | `host.cjs`: contexto parcial permanece intacto y error visible al consultar anamnesis |
| Un close nativo atrasado podía limpiar una nueva apertura | Evento close ignora un diálogo ya reabierto; epoch protege cargas anteriores | Volver a entrar rápidamente no destruye el nuevo estado | `host.cjs`: cierre/apertura seguidos y gate lento cancelado |
| El reviewer asignado no puede leer las revisiones privadas del owner por RLS | El adapter omite esa consulta y obtiene la propuesta mediante `premium_recommendation_view` | La revisión asignada carga sin ampliar permisos ni usar JWT del atleta | `reviewer-adapter.cjs local`: revisiones owner ausentes, hechos/cambios/warnings seguros, rechazo de owner sin prescripción y trainer no asignado |
| No leer check-ins o programación no demuestra que estén pendientes o vacíos | Home reviewer omite el estado de check-in y Mi programación; explica que el contexto permitido está en la propuesta | La falta de acceso no se presenta como una ausencia de hechos | `reviewer-ui.cjs`: ausencia de inferencias, propuesta visible y límite explícito ante navegación directa; owner conserva sus controles |
