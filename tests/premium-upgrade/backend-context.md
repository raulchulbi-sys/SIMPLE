# Phase 5: same-routine admission

The candidate adopts the existing accepted Basic routine. It does not create a copy, replace any exercise/day UUID, rewrite a Basic operation or revision, regenerate a plan, or modify workouts, notes or assignments. Active `routine_management.plan_kind` becomes `premium`; its original Basic `operation_id` remains the historical provenance. The original Basic revision is reused as both initial and current mesocycle revision, only after checking its stored hash and exact live identities/order/prescription. A mismatch rejects atomically. No inferred baseline is constructed.

Accepted Basic v2/v3/v4 snapshots use canonical `reps_min/reps_max`. The old Premium reader expected `target`, which is a live UI projection. The extension reads the accepted snapshot's canonical ranges directly for those legacy revisions. V5 `planned_sets` remains authoritative, including differing rep ranges, RIR zero and rest per set. Invalid or ambiguous series are rejected. No historical JSON is rewritten.

## Server access and user consent

Two new private tables have RLS enabled and no Data API table grants, including to service role:

- `premium_entitlements`: selected owner, OFF by default, expiry, capabilities, version, analysis/chat limits and lifetime consumed counters.
- `premium_admissions`: one admission per routine, source kind, exact original Basic operation/revision, mesocycle, consent grant, captured entitlement version and idempotency key.

`premium_set_entitlement(user,enabled,until,capabilities,generation_limit,analysis_limit,chat_limit)` is server-only. Capabilities are exactly `upgrade`, `tracking`, `weekly`, `analysis`, `chat`. An enabled entitlement must include tracking and a future expiry. Profile role remains `client`; authentication identity is unchanged. Generation allowance must be zero in this phase: adopting an existing routine does not generate a new one, and there is no Premium initial-generation endpoint.

The athlete explicitly accepts `premium-followup-v1` through `premium_admission_permission(allow,notice)`. This adds scope `premium_admission`, separately from the existing history, weekly and chat permissions. Revocation does not delete any delivered routine, workout or historical decision. A regrant creates a new grant identity; renewing/revoking server access changes its version. Neither can revive a captured request/recommendation from the old grant/version.

The delivered routine remains readable through the existing owner RLS when Premium access expires.

## Locking, quotas and stale state

New mutation wrappers acquire the existing Basic owner advisory lock, then the existing Premium grant advisory lock, followed by entitlement row, routine row and management row when admitting. Existing Premium operations sharing the grant lock serialize with admission/revocation; Basic operations sharing the Basic lock cannot cross an upgrade. A pending independent Basic operation blocks upgrade. Further Basic generation is rejected for Premium-managed users; the original accepted Basic call remains an idempotent read-only return.

Same routine/revision/period retries return the existing mesocycle. Conflicting keys, a changed expected revision, another owner, incompatible management, a changed baseline or changed admission parameters reject before partial creation.

Admission of a previously unmanaged owned routine also serializes with ordinary structure edits. The existing structure trigger now locks the affected parent routine(s), in UUID order, immediately before its unchanged management/internal-acceptance checks. Provision locks the same parent and reads descendant rows with MVCC; it does not acquire descendant row locks. This matters because an UPDATE may already hold an exercise-row lock when its BEFORE trigger runs. Making provision wait for that exercise row while retaining the parent could invert the lock order; the implementation avoids that combination. The trigger remains VOLATILE so its management check after a lock wait uses a fresh READ COMMITTED snapshot. An edit that commits first is fully reflected in the baseline; an edit behind an admission must be denied after management exists. Administrative maintenance and the existing cosmetic-routine shortcut remain unchanged, as does the acceptance transaction's explicit internal-write guard. Definition checks and a real overlapping-session test are separate evidence; a single-transaction SQL test alone does not establish concurrency behavior.

## Rollback

`rollback.sql` restores the exact saved Phase 4 definitions using CREATE OR REPLACE, preserving their original OIDs and ACLs. It refuses live admissions, captured operations, upgraded management or reserved provider costs. It never silently deletes or converts a live upgraded routine. Owner/global accounting survives disabled and is not reset on reapply.

For a full Phase 1–5 rollback, first validate each historical phase's compatibility guard and perform backups. Run Phase 5 rollback, then the Phase 4/3/2/1 rollbacks in reverse order. Each phase must stop if its own live-data guard fails; do not use CASCADE to bypass that condition. A production rollback is future work requiring deployment authorization and a concrete compatible state, not permission to delete production records.

`rollback-stack.cjs` generates an atomic staging rehearsal: global preflight before any DDL, rollback to the Basic checkpoint, exact candidate reapply, accounting restore, then comparison of function definitions/owner/ACL and 16 data inventories (seven central tables, stable Auth/users and identities, Basic operations/revisions/management/intakes/health/grants/feedback). The historical Phase 2 rollback drops its ledger; consequently the rehearsal stores the complete prior row temporarily and restores every column inside the same uncommitted transaction before any provider can observe a reset. Owner lifetime consumption is also compared exactly. Provider flags and owner access must be OFF before this rehearsal; live admissions or captured operations cause rejection.

Advisor review: private entitlement/admission tables intentionally have RLS with no API grants and no allow policy. Their default denial is part of the server-only design. SECURITY DEFINER endpoints are deliberately scoped by owner/server/reviewer checks and explicit EXECUTE ACLs. The new admission table's routine_id primary key covers its routine FK prefix; its mesocycle/user/key uniqueness and owner index cover the admission lookups used here. Additional FK indexes for baseline-operation/consent references are optional at this pilot scale; no blanket indexes or access policies are added merely to silence informational findings.

All current deployment work is staging only. Patatasimple in production remains an accepted Basic v2 routine with its original IDs/history. This implementation makes that architecture compatible in principle; it does not admit, convert, authorize, copy, generate for, approve for or accept for that account.
